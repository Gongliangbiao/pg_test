# PG 用例生成架构备忘

## 当前已明确的职责拆分

- `pg-doc-extract`：从官方文档抽取测试点，输出测试点概览。
- `pg-case-design`：把测试点概览补全为可生成 SQL 的用例设计。
- `pg-casegen`：根据用例设计生成 SQL 文件。
- `pg-sql`：提供 PostgreSQL 语法、参数和行为事实。
- `pg-sql-case-naming`：提供 SQL 文件路径、文件名和数据库对象名规范。

## 遗留问题：流程裁判角色

当前生成链路中缺少一个独立的“裁判”角色，用于判断每一步的产物是否符合预期。

这个角色不应直接负责生成内容，而应负责验收和阻断，例如：

- 判断测试点概览是否完整覆盖官方章节。
- 判断用例设计是否足够支撑 SQL 生成。
- 判断生成的 SQL 是否符合命名、对象缩写、会话数量、同步点、稳定性等项目规范。
- 判断 `pg-casegen` 是否在缺少必要输入时进行了不可靠推断。
- 判断每个阶段的输入输出是否满足约定契约。

## 暂不处理原因

当前优先级仍是梳理生成链路和输入契约。裁判角色会影响整体流程编排、检查规则和失败处理方式，适合作为后续独立设计项处理。

## 后续可能方向

后续可以考虑新增独立 skill，例如：

```text
pg-case-reviewer
```

该 skill 只负责检查，不负责生成。它可以在以下阶段介入：

```text
test-points -> review
case-designs -> review
sql -> review
```

目标是让整条链路形成：

```text
生成 -> 验收 -> 下一步生成
```

而不是一次性生成到底。
